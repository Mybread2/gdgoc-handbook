35분 — 무엇을 만들지 정하고, 서비스가 어떤 부품으로 되어 있는지

여는 말

오늘 뭘 할지

2분
[화면] 핸드북 홈

오늘은 코딩을 가르치는 시간이 아니에요. 곧 팀에 배정돼서 한두 달 안에 돌아가는 서비스를 하나 만들게 되는데, 그때 필요한 공통 언어를 맞추는 시간입니다.

여기 보이는 게 오늘 쓸 핸드북이에요. 여섯 갈래로 되어 있고, 오늘은 1번부터 3번까지 — 기초, 깃허브, 협업 — 여기까지 합니다. 인프라랑 로그인, AI 도구는 다음 시간에 할게요.

링크는 끝나고 공유할 거예요. 받아 적지 않으셔도 됩니다. 오늘 목표는 딱 하나, 팀 활동에서 멘토가 하는 말을 알아듣는 것입니다.

가볍게 손 들어 보게 하기: “깃허브 계정 있으신 분?” / “코딩 처음이신 분?” — 분위기도 풀리고, 뒤에서 설명 깊이를 조절할 수 있어요.
1.1

시작하기 전에

3분
[화면] 1.1 설치할 것 세 가지

먼저 준비물부터. 세 개예요. Antigravity, Git, GitHub 계정. 전부 무료입니다.

Antigravity는 코드를 쓰는 프로그램이에요. 구글이 만든 건데, AI 에이전트가 처음부터 들어 있어서 따로 결제할 게 없습니다. VS Code 쓰시던 분은 그거 쓰셔도 돼요. 사실 Antigravity가 VS Code를 바탕으로 만든 거라 화면이 거의 똑같습니다.

유료 구독은 안 하셔도 됩니다. 이거 꼭 말씀드리고 싶었어요. Claude나 ChatGPT 결제 안 해도 프로젝트 끝까지 만들 수 있어요. 더 깊게 파고 싶은 사람만 나중에 고민하세요.

[화면] 1.1 처음 한 번 해 둘 설정

그리고 설치하고 나서 5분이면 끝나는 설정이 네 개 있는데, 여기 적어 뒀어요. 안 해 두면 첫 주에 한 번씩 막히는 것들입니다. Git에 이름·이메일 등록됐는지 확인하기, 작업 폴더는 영문 경로에 두기 — OneDrive 안에 두지 마세요, 윈도우는 파일 확장자 보이게 켜기, 한국어 언어 팩 깔기.

넘어가는 말: “설치는 각자 해 오시고, 안 되면 팀 채널에 물어보세요. 자, 그럼 본론입니다.”
1.2

개발자는 무슨 일을 하는 사람인가

10분
[화면] 1.2 가장 중요한 한 문장

오늘 제일 중요한 문장부터 보여 드릴게요. “개발자는 주어진 시간과 예산 안에서 문제를 소프트웨어로 해결하는 사람이다.”

여기서 눈여겨볼 게 있어요. 이 문장에 ‘코딩’이라는 말이 없습니다. 개발자는 코딩을 잘하는 사람이 아니라, 제약 안에서 문제를 푸는 사람이에요. 이 차이가 오늘 내내, 그리고 여러분 팀 프로젝트 내내 따라다닐 겁니다.

[화면] 1.2 세 덩어리가 들어 있습니다

문장을 뜯어보면 세 덩어리예요. 문제, 시간과 예산, 소프트웨어로 해결.

첫째, 누군가 불편한 게 있어야 시작해요. “무슨 기술 써볼까”로 시작한 프로젝트는 대부분 중간에 멈춥니다. 풀 문제가 없으니까 어디까지 만들어야 하는지도 모르거든요.

둘째, 제약은 항상 있어요. 시간도 사람도 정해져 있고, 돈은 거의 없죠. 셋째, 소프트웨어는 수단이지 목적이 아니에요. 엑셀로 5분이면 되는 일에 두 달짜리 시스템을 만들면 그건 잘못 푼 겁니다.

[화면] 1.2 “제일 좋은 기술”은 없습니다 (표)

그래서 제일 좋은 기술 같은 건 없어요. 여기 같은 중고 거래 서비스를 만드는 두 팀이 있어요. 왼쪽은 1년에 개발자 10명, 오른쪽은 두 달에 4명, 예산 0원.

왼쪽은 로그인을 직접 만들고, 결제도 직접 연동하고, 검색 엔진도 붙여요. 오른쪽은 구글 로그인 갖다 붙이고, 결제는 아예 안 만들고 채팅으로 직거래하게 하고, 검색은 제목 일치만 합니다.

오른쪽이 실력이 부족해서 저렇게 하는 게 아니에요. 제약에 맞는 판단을 한 겁니다. 두 달짜리 팀이 왼쪽을 따라 하면 아무것도 완성 못 해요.

[화면] 1.2 이것이 여러분이 가진 전부입니다

그럼 여러분의 제약은 뭘까요. 시간은 한두 달, 사람은 몇 명, 대부분 개발이 처음이고 수업이랑 병행하죠. 돈은 거의 0원.

그래서 여러분의 성공 기준은 “완벽한 서비스”가 아닙니다. 기간이 끝났을 때 실제로 돌아가는 게 있느냐예요. 작아도 돌아가는 게, 크지만 안 돌아가는 것보다 낫습니다. 언제나요.

질문 던지기: “여러분이 지금 당장 불편한 거 하나만 말해 볼래요?” — 나온 대답 하나를 잡아서 뒤의 설계 설명에 계속 써먹으면 훨씬 잘 붙어요.
1.3

설계 — 코드보다 먼저 하는 일

12분
[화면] 1.3 언어를 아는 것과 만들 수 있는 것은 다릅니다

두 번째로 중요한 문장이에요. “개발자는 언어를 아는 사람이 아니라 시스템을 설계할 수 있는 사람이다.”

문법은 며칠이면 훑어요. 그런데 문법 다 외운 사람한테 “서비스 하나 만들어 보세요” 하면 첫 줄을 못 씁니다. 왜일까요. 무엇을 만들지, 어떤 부품으로 나눌지, 데이터를 어떻게 담을지가 안 정해졌기 때문이에요. 이 셋을 정하는 게 설계고, 코드를 한 줄도 안 쓴 상태에서 합니다.

[화면] 1.3 무엇을 안 만들지 정하는 일

그런데 설계의 절반은 안 만들 것을 정하는 일이에요. 예를 들어 학식 리뷰 서비스를 두 달 안에 만든다고 해 봅시다. 아이디어 회의하면 기능이 스무 개쯤 나와요. 여기서 네 개만 남깁니다.

식당 목록이랑 오늘 메뉴 보기, 별점이랑 한 줄 평 남기기, 남이 쓴 평 보기, 로그인. 끝이에요.

오른쪽은 다 지웁니다. 사진 업로드, 댓글, 알림, 검색, 관리자 페이지, 랭킹. 이걸 지우는 게 초보 팀이 가장 못 하는 일이자 가장 중요한 일이에요. 전부 만들려다 아무것도 못 끝내는 팀이 매년 나옵니다.

버리는 게 아니라 미루는 거예요. 왼쪽이 돌아간 다음에 하면 됩니다.

[화면] 1.3 문제 하나를 만들 수 있는 조각으로 (그림)

설계가 실제로 하는 일을 그림으로 보면 이래요. 맨 위에 문제 하나 — “오늘 학식 뭐 나오는지, 맛있는지 모르겠다”. 이게 만들 기능 네 개로 쪼개지고, 그게 다시 사람이 보는 화면이랑 기억해야 할 데이터로 갈라집니다.

여기까지 하면 “내일부터 누가 뭘 할지”가 정해져요. 코드는 그다음입니다.

[화면] 1.3 데이터를 어떻게 담을지 (표)

그중에서도 데이터 구조가 제일 나중에 고치기 어려워요. 화면은 나중에 바꾸면 되는데, 데이터는 한번 쌓이기 시작하면 바꾸기가 힘듭니다. 그래서 여기에 시간을 더 씁니다.

요령 하나 드릴게요. “한 줄이 무엇 하나를 뜻하는지” 말할 수 있으면 잘 나눈 거예요. 식당 표는 한 줄이 식당 하나, 메뉴 표는 한 줄이 “9월 16일 학생식당 제육덮밥”. 만약 “식당이면서 메뉴이기도 한 표”가 나오면 다시 나눠야 한다는 신호입니다.

시간 없으면: 데이터 표는 “이런 게 있다” 정도로 20초만 보여주고 넘어가도 됩니다. 대신 안 만들 것 정하기는 절대 빼지 마세요 — 오늘 1부에서 제일 실전적인 내용이에요.
1.4

서비스는 어떤 부품으로 되어 있나

10분
[화면] 1.4 화면 · 판단 · 기억 (그림)

설계한 걸 실제로 만들려면 부품 이름을 알아야 해요. 거의 모든 서비스가 이 세 덩어리입니다. 화면을 그리는 곳, 판단하는 곳, 기억하는 곳.

각각 프론트엔드, 백엔드, 데이터베이스라고 부릅니다. 프론트엔드는 브라우저나 앱에서 돌고, 백엔드는 서버에서 돌고, 데이터베이스는 껐다 켜도 남아 있어요. 사이에 요청과 응답이 오갑니다.

중요한 건 사용자는 프론트엔드까지만 볼 수 있다는 거예요. 웹이든 앱이든 이 구조는 같습니다. 바뀌는 건 맨 왼쪽이 브라우저냐 스마트폰이냐뿐이에요.

[화면] 1.4 부품마다 할 수 있는 일이 다릅니다

부품마다 할 수 있는 일이 달라요. 여기서 제일 자주 나는 실수를 하나 짚고 갈게요.

프론트엔드에서 막은 건 막은 게 아닙니다. 삭제 버튼을 안 보이게 숨겨도, 요청 주소만 알면 그냥 보낼 수 있어요. 브라우저 코드는 사용자 겁니다. 그래서 중요한 검사는 반드시 백엔드에서 한 번 더 해야 해요. 이건 다음 시간 인가 파트에서 다시 나옵니다.

[화면] 1.4 API — 화면과 서버 사이의 약속

이 부품들을 잇는 게 API예요. 어려운 말 같지만 “이렇게 물어보면 이렇게 답한다”는 약속일 뿐입니다. 화면 쪽이랑 서버 쪽이 서로 속을 몰라도 돼요.

여기 예시 보시면, 화면에서 “3번 식당의 9월 16일 메뉴 줘” 하고 물어보면 서버가 메뉴 목록을 이런 모양으로 돌려줍니다.

이 약속을 먼저 정해두면 좋은 점이 있어요. 서버를 아직 안 만들었어도 화면부터 시작할 수 있습니다. 저 모양의 가짜 데이터로요. 두 달짜리 팀한테 이건 시간을 버는 기술이에요.

[화면] 1.4 여러분은 양쪽을 다 만듭니다

마지막으로 이 프로그램의 방침 하나. “나는 화면 할게, 너는 서버 해” — 이렇게 안 나눕니다. 팀원 모두가 화면부터 데이터까지 한 바퀴를 돕니다.

이유가 몇 개 있는데 제일 중요한 건 이거예요. 전체를 못 보면 설계를 못 합니다. 화면만 아는 사람은 데이터를 어떻게 담을지 정할 수 없어요. 그리고 두 달짜리 팀에서 한 명이 바빠지면 그 층이 통째로 멈춥니다.

깊게 파는 건 나중에 언제든 할 수 있어요. 한 바퀴를 직접 도는 경험은 지금이 아니면 잘 안 옵니다.

30분 — 레포 → 브랜치 → 커밋 → PR → 머지, 실제 화면으로 한 바퀴

2.1

Git과 GitHub

8분
[화면] 2.1 보고서_최종_진짜최종_v2_수정.hwp

이 파일 이름 보고 웃으셨다면, 이미 이 문제를 겪어 보신 거예요. 이게 정확히 개발자들이 겪던 문제입니다. 코드에서는 훨씬 심각해져요.

어제는 됐는데 오늘 안 되고, 뭘 바꿨는지 기억이 안 나고, 되돌리고 싶은데 어디까지 되돌려야 할지 모르고. 팀이면 더해요. 누가 언제 뭘 고쳤는지 아무도 모릅니다. 파일을 카톡으로 주고받으면 반드시 누가 덮어씁니다.

Git이 이걸 한꺼번에 해결해요. 언제, 누가, 무엇을, 왜 바꿨는지를 전부 기록하고, 아무 시점으로나 되돌아갈 수 있게 합니다.

[화면] 2.1 커밋 = 저장점 + 메모

그 기록 하나하나를 커밋이라고 불러요. 게임 세이브 포인트를 떠올리시면 되는데, 다른 게 하나 있어요. “여기서 무엇을 왜 했는지” 메모가 반드시 붙습니다.

감 잡는 기준 하나. 한 커밋은 한 가지 일. “로그인 버그 수정”이랑 “버튼 색 변경”은 따로 커밋해야 해요. 섞으면 되돌릴 때 같이 딸려옵니다.

[화면] 2.1 2주 뒤의 나에게 쓰는 편지

커밋 메시지는 2주 뒤의 나한테 쓰는 편지라고 생각하세요. 왼쪽처럼 “수정”, “ㅇㅇ”, “asdf” 이렇게 쓰면 아무 도움이 안 됩니다.

오른쪽처럼 “리뷰 작성 시 별점 없이 제출되던 문제 수정” — 이렇게요. 판단 기준은 하나예요. 2주 뒤의 내가 이 메시지만 보고 “아 그거” 하고 떠올릴 수 있으면 합격. 한국어로 쓸지 영어로 쓸지는 팀이 정하면 됩니다. 섞어 쓰지만 않으면 돼요.

[화면] 2.1 Git과 GitHub은 다릅니다

그리고 자주 헷갈리는 거 하나. Git이랑 GitHub은 다릅니다. Git은 내 컴퓨터에 까는 도구고, GitHub은 그 기록을 올려두고 공유하는 웹사이트예요.

비유하자면 Git은 카메라, GitHub은 사진 올리는 곳. 팀 프로젝트에서는 둘 다 씁니다. 각자 카메라로 찍고, 한 곳에 모으는 거죠.

2.2

레포지토리

4분
[화면] 2.2 레포지토리가 뭔가요

이제 실제 화면으로 갈게요. 먼저 단어 하나. 레포지토리, 줄여서 레포. 프로젝트 폴더 + 모든 변경 기록입니다. 팀 프로젝트 하나에 레포 하나 만들고, 팀원 모두가 여기에 올려요.

[화면] 2.2 새 레포 만들기 (스크린샷 3장)

만드는 건 간단해요. 오른쪽 위 플러스 → New repository. 이름은 영문 소문자랑 하이픈으로 짓는 게 관례입니다. 초록색으로 사용 가능하다고 뜨면 되는 거예요.

아래로 내려서 Add README를 켜는 걸 권합니다. 레포 첫 화면에 보이는 설명 파일인데, 켜 두면 빈 레포가 아니라서 바로 브랜치를 만들 수 있어요.

만들면 이런 화면이 나와요. 왼쪽 위 main이 지금 보고 있는 브랜치, 오른쪽 1 Commit이 지금까지 쌓인 기록입니다.

팀에서는 한 명이 레포를 만들고 Settings → Collaborators에서 팀원을 초대하면 돼요.

2.3

브랜치

7분
[화면] 2.3 브랜치는 “내 복사본에서 작업하기” (그림)

여기서부터가 여럿이 일하는 이야기예요. 브랜치는 한마디로 내 복사본에서 작업하기입니다.

그림 보시면, 가운데 main이 있고 A는 위로, B는 아래로 갈라져 나가서 각자 작업해요. A가 리뷰 기능 만드는 동안 B는 로그인을 만드는데 서로 영향이 없습니다. 다 되면 리뷰를 거쳐서 다시 main으로 합쳐지고요.

핵심은 이거예요. 내 브랜치에서 아무리 망가뜨려도 남의 작업이랑 돌아가는 버전은 멀쩡합니다.

[화면] 2.3 두 달짜리 팀은 단순하게 가세요

브랜치 전략은 종류가 많은데, 회사에서 쓰는 복잡한 걸 그대로 가져오면 배우는 데만 한 주를 씁니다. 여러분은 맨 윗줄, main 하나에 각자 feature/○○면 충분해요.

규칙은 두 줄이면 됩니다. 하나, main에 직접 push 하지 않는다. 둘, 작업은 항상 새 브랜치에서 한다. 그리고 main은 언제든 돌아가는 상태로 유지하세요. 발표 전날 여기가 깨져 있으면 답이 없습니다.

[화면] 2.3 내 브랜치 만들기 (스크린샷 2장)

만드는 건 화면 그대로예요. main 버튼 누르고, 검색 칸에 새 이름을 입력하면 Create branch … from main이 뜹니다. 그거 누르면 끝이에요.

이름은 보면 무슨 작업인지 알게 지으세요. feature/add-intro, fix/login-redirect 이런 식으로요.

만들고 나면 왼쪽 위가 바뀌고 2 Branches가 됩니다. “This branch is up to date with main” — 아직은 main이랑 똑같은 복사본이라는 뜻이에요.

2.4

내 브랜치에서 작업하기

4분
[화면] 2.4 파일 고치고 커밋하기

실제로는 내 컴퓨터 에디터에서 코드를 고치지만, 흐름을 보여드리려고 여기서는 GitHub 웹에서 바로 고쳐 볼게요. 순서는 똑같습니다. 고치고, 커밋하고.

연필 아이콘 누르면 편집 화면이 열려요. 위에 in feature/add-intro 보이시죠. 지금 내 브랜치를 고치고 있다는 표시입니다.

다 고치면 Commit changes 누르고, 메시지 적고, 아래 선택지는 “내 브랜치에 커밋” 그대로 두고 확인. 참고로 Copilot이 메시지를 영어로 자동으로 채워 주기도 하는데, 팀이 정한 형식이 있으면 그걸 따르세요.

[화면] 2.4 main은 아직 그대로입니다

자, 여기가 오늘 2부에서 제일 보여드리고 싶은 화면이에요. 레포 첫 화면으로 돌아오면 위에 “방금 브랜치에 뭔가 올라갔다”는 알림이 뜨는데, 아래 main에는 여전히 커밋이 하나뿐입니다.

이게 브랜치를 쓰는 이유예요. 내 작업은 내 브랜치에만 있고, 모두가 쓰는 main은 멀쩡합니다.

2.5

PR 올리기

5분
[화면] 2.5 “이거 합쳐도 될까요?”라고 묻는 자리

그럼 main에는 어떻게 넣느냐. Pull Request, 줄여서 PR을 올립니다. 이름이 어려운데 하는 일은 단순해요. “내 브랜치를 main에 합쳐도 될까요?”라고 팀에 묻는 글입니다.

왜 한 단계를 더 거치냐면, 바뀐 줄이 전부 보이고, 다른 사람이 읽고, 기록이 남기 때문이에요. 나만 아는 코드가 줄어듭니다. 팀원 한 명이 아프면 프로젝트가 멈추는 상황을 막아 줘요.

그리고 이거 꼭 말씀드릴게요. PR은 검사받는 자리가 아니라 공유하는 자리예요. 실력을 평가하는 게 아니라, 팀이 코드를 같이 아는 게 목적입니다.

[화면] 2.5 PR 만들기 · PR 화면 읽기

아까 그 초록 버튼 누르면 이 화면이 나와요. 맨 위 줄부터 보세요. base: main ← compare: feature/add-intro. “이 브랜치를 main으로”라는 뜻입니다. Able to merge는 충돌 없이 합칠 수 있다는 뜻이고요.

제목이랑 설명을 쓰는데, 설명에는 무엇을 바꿨는지랑 리뷰어가 뭘 확인해 주면 좋은지를 적으세요.

올리고 나면 이렇게 열립니다. 탭이 네 개인데, 리뷰어가 제일 오래 보는 건 Files changed예요. 초록 줄이 추가, 빨간 줄이 삭제고, 줄 번호 옆을 누르면 그 줄에 바로 코멘트를 달 수 있습니다.

2.6

main에 머지하기

2분
[화면] 2.6 main에 합치기 → 결과 확인

리뷰가 끝나고 팀이 좋다고 하면 합칩니다. No conflicts 확인하고, Merge 누르고, Confirm 누르면 끝이에요. 상태가 보라색 Merged로 바뀝니다.

main으로 가 보면 내용이 반영돼 있고 커밋 수가 늘어 있어요. 한 바퀴 정리하면 — 레포에서, 내 브랜치 만들고, 거기서 고치고 커밋하고, PR 올리고, 리뷰 후 머지. 팀 프로젝트 내내 이 다섯 단계를 반복합니다.

넘어가는 말: “도구는 여기까지예요. 그런데 진짜 어려운 건 도구가 아니라 사람끼리 맞추는 것입니다. 3부에서 그 이야기를 할게요.”

3부 · 협업하는 법

20분 — 리뷰를 주고받고, 일을 나누고, 팀 약속을 정하는 법

3.1

리뷰 주고받기

7분
[화면] 3.1 PR은 한 번에 통과하지 않습니다 (그림)

먼저 마음의 준비부터. PR은 한 번에 통과하지 않습니다. 그림에서 되돌아오는 화살표 두 개 보이시죠. 자동 검사에서 막히거나, 리뷰에서 “여기 이렇게 해볼까요?”가 오면 고쳐서 다시 올려요. 이게 정상입니다. 한 번에 통과하는 PR이 오히려 드물어요.

[화면] 3.1 같은 지적도 쓰기 나름입니다

그런데 리뷰는 말로 하는 거라 쓰기 나름이에요. 왼쪽처럼 “이거 왜 이렇게 했어요?”, “코드가 이상한데요”, “이건 기본 아닌가요?” — 이러면 팀이 상합니다.

오른쪽처럼 쓰세요. “여기 별점이 없을 때 에러가 날 것 같은데, 확인해 주실 수 있을까요?” 이렇게요.

규칙 셋만 기억하면 돼요. 하나, 코드를 지적하지 사람을 지적하지 않는다. 둘, 무엇이 문제인지 구체적으로 쓴다. 셋, 사소한 지적은 사소하다고 밝힌다.

마지막 게 특히 중요해요. 오타 지적이랑 설계 지적이 같은 무게로 읽히면 받는 사람이 지칩니다. “(사소함) 오타인 것 같아요” 이렇게 한마디만 붙이면 됩니다.

[화면] 3.1 리뷰를 받을 때

받는 쪽도 봅시다. 첫 번째 관문은 이거예요. 지적은 코드에 대한 것이지 나에 대한 평가가 아닙니다. 이걸 분리하는 게 처음엔 잘 안 돼요.

그리고 동의하지 않으면 말해도 됩니다. “이건 이런 이유로 이렇게 했습니다”는 완전히 정당해요. 리뷰는 대화지 심사가 아니에요. 모르면 예시를 달라고 하시고, 고쳤으면 “반영했습니다” 한 줄 남겨 주세요.

마지막으로 하나. 경력 10년차도 리뷰에서 지적받습니다. 지적받는 횟수는 실력과 상관없어요. 상관있는 건 같은 지적을 두 번 받는지입니다.

3.2

일 나누기

7분
[화면] 3.2 가로로 자르지 말고 세로로 자르세요 (그림)

여기가 팀 프로젝트가 늘어지는 가장 큰 이유가 있는 곳이에요. 같은 인원이 같은 걸 만들어도 자르는 방향에 따라 결과가 달라집니다.

왼쪽이 가로로 자르기. A는 화면, B는 서버, C는 데이터. 이러면 A는 B가 끝나야 눌러볼 수 있어요. 서로 기다리게 됩니다. 그리고 각자 자기 층만 배우게 돼요.

오른쪽이 세로로 자르기. A는 리뷰 기능을 화면부터 데이터까지, B는 로그인을 화면부터 데이터까지. 각자 끝까지 혼자 갈 수 있고, 양쪽을 다 배웁니다.

1부에서 “여러분은 양쪽을 다 만듭니다” 했던 게 여기랑 연결돼요. 그리고 이렇게 나누면 API 약속이 팀원 사이의 경계에서 필요해집니다. B가 만든 로그인을 A의 리뷰 기능이 쓸 때요.

[화면] 3.2 무엇을 기준으로 쪼갤까 (표)

기준은 기능 단위가 제일 무난하고, 화면 단위도 괜찮아요. 층 단위만 피하시면 됩니다.

정답은 없는데, 하나만 지키세요. “이번 주에 내가 끝낼 것”이 한 문장으로 말해져야 합니다.

[화면] 3.2 이슈 — 누가 뭘 하고 있는지

그리고 할 일 관리. GitHub에 이슈라는 게 있어요. 할 일 하나를 글 하나로 만들고, 담당자 붙이고, 끝나면 닫습니다.

카톡으로 관리하지 마세요. 스크롤 올리다 사라집니다. 이슈 하나는 한 사람이 며칠 안에 끝낼 수 있는 크기로요. “로그인 만들기”는 너무 큽니다.

도구는 노션이든 지라든 뭐든 상관없어요. 중요한 건 “한 곳에만 있을 것”입니다. 두 군데 적으면 반드시 어긋나요.

3.3

팀 약속과 질문하는 법

6분
[화면] 3.3 팀이 합의해야 할 것들 (체크리스트)

팀 배정되면 첫 모임에서 이 여섯 개를 정하고 시작하세요. 브랜치·커밋 규칙, 합치는 조건, 일 나누는 기준, 모이는 시간, 막혔을 때 혼자 몇 시간까지 붙들지, 코드 스타일.

저는 “막혔을 때”를 제일 강조하고 싶어요. 예를 들어 두 시간. 그 이상 혼자 붙들지 않기로 정해두면 팀 전체 속도가 달라집니다.

이거 정하는 데 한 시간이면 충분해요. 안 정하고 시작하면 매번 다시 의논하느라 훨씬 더 씁니다.

[화면] 3.3 막혔을 때 잘 물어보는 법

마지막으로 오늘 제일 실전적인 기술입니다. 이걸 잘하는 사람이 제일 빨리 늘어요.

“안 돼요”, “에러 나요”, 스크린샷 한 장 덜렁 — 이러면 도와주고 싶어도 못 도와줘요. 네 가지를 같이 적으세요. 뭘 하려고 했는지, 뭘 했는지, 뭐가 나왔는지 — 에러 메시지는 전문 그대로 — 그리고 뭘 시도해 봤는지.

부작용이 하나 있는데요, 이걸 적다가 스스로 답을 찾는 경우가 절반쯤 됩니다. 정리하는 과정 자체가 디버깅이에요.

[화면] 3.3 협업, 세 문장으로

3부를 세 문장으로 정리하면 이렇습니다. 커밋은 저장점이 아니라 기록이고, PR은 검사가 아니라 공유고, 일을 나누는 방식이 프로젝트 속도를 정합니다.

오늘 닫는 말 · 1분

오늘 한 걸 한 문장으로 하면 — “코딩을 시작하기 전에 정해야 하는 것들과, 여럿이 같이 만들 때 필요한 약속”이었어요.

팀 배정되면 첫 주에 코딩부터 시작하지 마세요. 문제를 정하고, 안 만들 것을 정하고, 데이터를 그려보고, 팀 약속을 정하고, 그다음에 시작하세요. 한 시간이면 됩니다.

핸드북 링크는 지금 채널에 올릴게요. 다음 시간에는 인프라, 로그인, AI 도구를 합니다. 그때까지 설치 세 개만 해 오시면 돼요. 질문 있으신 분?
