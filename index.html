강의 전에 미리

설치할 것 세 가지

개발이 처음이어도 괜찮습니다. 아래 셋만 깔려 있으면 팀 활동 첫날 바로 시작할 수 있어요. 돈은 한 푼도 들지 않습니다.

  1. Antigravity 설치 — 코드를 쓰는 프로그램(에디터)입니다. antigravity.google/download에서 내 운영체제용을 받아 설치하고, 구글 계정으로 로그인하면 끝입니다. 무료이고, AI 에이전트가 처음부터 들어 있습니다.
  2. Git 설치 — 코드의 변경 기록을 남기는 도구입니다. git-scm.com/downloads. 설치 후 터미널에서 git --version 을 쳤을 때 버전이 나오면 성공입니다.
  3. GitHub 계정 — 팀이 코드를 모아 두는 곳입니다. 학교 이메일로 가입해 두면 다음 항목이 수월합니다.
유료 구독은 하지 않아도 됩니다. Antigravity에 들어 있는 에이전트만으로 팀 프로젝트를 끝까지 만들 수 있습니다. Claude·ChatGPT 구독은 더 깊게 파고 싶은 사람의 선택이지, 준비물이 아닙니다.
왜 Antigravity인가요? 개발자들이 가장 많이 쓰는 VS Code를 바탕으로 만든 에디터라서 화면과 단축키가 거의 같고, 따로 결제하거나 설정하지 않아도 AI 에이전트가 이미 붙어 있습니다. 이미 VS Code를 쓰고 있다면 그대로 쓰셔도 됩니다 — 이 핸드북의 설명은 양쪽 모두에 그대로 적용됩니다.

1

Git에 내 이름과 이메일이 등록되어 있는지 확인
안 되어 있으면: 터미널에서 첫 커밋을 할 때 Please tell me who you are 에러가 나고 커밋이 안 됩니다.
먼저 아래를 쳐서 user.name과 user.email이 보이는지 확인하세요.

git config --global --list

안 보이면 등록합니다. 이메일은 GitHub에 가입한 이메일로 적으세요 — 커밋에 “누가 했는지”로 찍히는 정보입니다.

git config --global user.name "Hong Gildong"
git config --global user.email "gildong@inha.edu"
git config --global init.defaultBranch main

이미 되어 있는 사람도 많습니다. GitHub Desktop이나 일부 IDE는 처음 커밋할 때 대신 등록해 주거든요. 반대로 GitHub 로그인만으로는 채워지지 않습니다 — 로그인은 “이 레포에 올릴 권한이 있느냐”(인증)이고, 이 설정은 “이 커밋을 누가 만들었느냐”(작성자)라서 서로 다른 것입니다.

작업 폴더는 영문 경로에
안 하면: 한글·공백이 섞인 경로나 클라우드 동기화 폴더(OneDrive·iCloud·구글 드라이브) 안에서는 도구가 파일을 못 찾거나 동기화와 충돌해, 원인을 알 수 없는 에러가 납니다.

안 하면: 메뉴가 전부 영어라 이 핸드북의 화면(파일 → 폴더 열기)과 이름이 달라 보입니다.

언어와 런타임(예: Node.js, Java, Python)은 지금 깔지 마세요. 팀이 무엇으로 만들지 정한 다음에, 멘토와 함께 필요한 것만 설치하면 됩니다. 미리 이것저것 깔면 버전이 꼬여서 시작이 더 느려집니다.

“코딩을 잘하는 사람”이 아닙니다. 제약 안에서 문제를 푸는 사람입니다. 이 차이가 이 핸드북 내내, 그리고 팀 프로젝트 내내 따라다닙니다.

문장을 뜯어보면

세 덩어리가 들어 있습니다

① 문제

누군가 불편한 것이 있어야 시작합니다.

“무슨 기술을 써볼까”로 시작한 프로젝트는 대부분 중간에 멈춥니다. 풀 문제가 없으니 어디까지 만들어야 할지도 모릅니다.

② 시간과 예산

제약은 항상 있습니다.

시간은 유한하고, 사람 수도 정해져 있고, 돈은 거의 없습니다. 제약이 없는 개발은 존재하지 않습니다.

③ 소프트웨어로 해결

수단입니다. 목적이 아닙니다.

엑셀로 5분이면 되는 일에 두 달짜리 시스템을 만들면, 그건 잘못 푼 겁니다.

그런데 “코딩”은 이 문장 어디에도 없습니다. 코딩은 ③번을 실행하는 수단 중 하나일 뿐입니다. 실제 업무 시간에서 코드를 치는 시간은 생각보다 적습니다.

제약이 답을 바꾼다

“제일 좋은 기술”은 없습니다

같은 서비스를 만들어도 제약이 다르면 정답이 달라집니다. 아래는 똑같은 “중고 거래 서비스”를 만드는 두 팀입니다.

오른쪽이 실력이 부족해서 저렇게 하는 게 아닙니다. 제약에 맞는 판단을 한 겁니다. 두 달짜리 팀이 왼쪽을 따라 하면 아무것도 완성하지 못합니다.

API — 화면과 서버 사이의 약속

화면 쪽과 서버 쪽은 서로의 속을 몰라도 됩니다. “이렇게 물어보면 이렇게 답한다”만 정하면 됩니다. 한 사람이 양쪽을 다 만들 때도 마찬가지입니다 — 먼저 정해두면 순서가 생깁니다.

# 화면에서 이렇게 물어보면
GET /api/restaurants/3/menus?date=2026-09-16

# 서버가 이렇게 답한다
{
  "menus": [
    { "id": 17, "name": "제육덮밥", "price": 5000,
      "avgRating": 4.2, "reviewCount": 31 }
  ]
}
이 약속을 먼저 정해두면 서버를 아직 안 만들었어도 화면부터 시작할 수 있습니다 — 저 모양의 가짜 데이터로요. 순서에 막히지 않는다는 뜻이고, 두 달짜리 팀에게 이건 시간을 버는 기술입니다.

이 프로그램의 방침

여러분은 양쪽을 다 만듭니다

“나는 화면 할게, 너는 서버 해” — 이렇게 나누지 않습니다. 팀원 모두가 화면부터 데이터까지 한 바퀴를 돕니다.

  • 전체를 못 보면 설계를 못 합니다. 앞에서 내내 이야기한 그것 — 화면만 아는 사람은 데이터를 어떻게 담을지 정할 수 없습니다.
  • 한쪽만 하면 상대를 이해하지 못합니다. “그건 서버에서 해주세요”가 얼마나 큰 일인지 모른 채 말하게 됩니다.
  • 두 달 팀에서는 위험합니다. 한 명이 바빠지면 그 층이 통째로 멈춥니다.
  • 깊게 파는 건 나중에 언제든 할 수 있습니다. 한 바퀴를 직접 도는 경험은 지금이 아니면 잘 오지 않습니다.
그래서 일은 “화면 담당 / 서버 담당”이 아니라 기능 단위로 나눕니다. “A는 리뷰 기능을 화면부터 데이터까지, B는 로그인을 화면부터 데이터까지.” 어떻게 나누는지는 “일 나누기” 장에서 자세히 봅니다.
프론트엔드 · 백엔드 · 데이터베이스와 API를 더 자세히 보려면 인프라 파트의 “3-Tier 아키텍처” · “API” 장으로.

1

팀이 정할 것 ①

브랜치 전략은 종류가 많습니다. 회사에서 쓰는 복잡한 방식을 그대로 가져오면 배우는 데만 한 주를 씁니다.

방식구성어울리는 곳
단순형main + 각자 feature/○○여러분 같은 소규모 단기 팀

그 이상릴리스·핫픽스 브랜치까지규모 있는 조직
  • 규칙은 두 줄이면 충분합니다. ① main에 직접 push 하지 않는다 ② 작업은 항상 새 브랜치에서 한다
  • 브랜치 이름은 보면 무슨 작업인지 알게 — feature/review-write, fix/login-redirect

왜 한 단계를 더 거치나

“이거 합쳐도 될까요?”라고 묻는 자리

내 브랜치 작업이 끝나면 바로 합치지 않습니다. PR을 열어 팀에 보여주고 나서 합칩니다.

  • 바뀐 줄이 전부 보입니다. 무엇을 건드렸는지 한눈에 드러납니다.
  • 다른 사람이 읽습니다. 나만 아는 코드가 줄어듭니다 — 팀원이 아프면 프로젝트가 멈추는 상황을 막습니다.
  • 기록이 남습니다. 나중에 “이거 왜 이렇게 했지?”의 답이 PR에 있습니다.
  • 자동 검사를 붙여두면 기계가 먼저 걸러줍니다.
PR은 검사받는 자리가 아니라 공유하는 자리입니다. 실력을 평가하는 게 아니라, 팀이 코드를 같이 아는 것이 목적입니다.

출발점

코드를 다 짜고 실행하면 내 화면에 서비스가 뜹니다. 그런데 이 주소는 나만 볼 수 있습니다.

  • 친구에게 주소를 보내면? 친구 본인 컴퓨터를 가리킵니다. 안 열립니다.
  • 내 노트북을 닫으면? 서비스가 사라집니다.
  • 발표 날 노트북이 꺼지면? 시연이 안 됩니다.
그래서 필요한 게 셋입니다. ① 꺼지지 않는 컴퓨터 ② 남들이 찾아올 주소 ③ 코드를 거기로 옮기는 방법. 이걸 통틀어 인프라라고 부릅니다.

꺼지지 않는 컴퓨터

서버는 특별한 물건이 아닙니다

그냥 끄지 않는 컴퓨터입니다. 모니터도 키보드도 없이, 인터넷에 연결된 채 24시간 켜져 있을 뿐입니다.

직접 사면
  • 컴퓨터값 + 전기요금 + 인터넷 회선
  • 고장 나면 내가 고쳐야 함
  • 사람이 몰려도 못 늘림
  • 두 달짜리 팀에게는 비현실적
빌리면 — 클라우드
  • 몇 분이면 생김
  • 쓴 만큼만 냄, 무료 구간이 있음
  • 고장·전기·회선은 남이 책임
  • 안 쓰면 지우면 끝
클라우드는 신비로운 기술이 아니라 임대업입니다. AWS, Google Cloud, Azure 같은 회사가 컴퓨터를 빌려줍니다.

예산 0인 팀의 현실적 선택

직접 만들 것인가, 빌려올 것인가

아래 네 가지는 전부 직접 만들 수도 있고, 전부 빌려 쓸 수도 있습니다. 두 달짜리 팀의 답은 대체로 한쪽으로 기웁니다.

필요한 것직접 하면빌리면두 달 팀
화면 배포서버 설치·설정Vercel, Netlify 등 무료 구간빌린다
서버 실행클라우드 서버 직접 세팅Render, Railway, Cloudtype 등빌린다
데이터베이스설치·백업·보안 직접Supabase, Firebase 등빌린다
로그인회원가입·비번찾기·인증메일구글 로그인, Firebase Auth 등빌린다
직접 만드는 것은 “우리 서비스에만 있는 것”에 씁니다. 로그인은 어느 서비스에나 있습니다 — 거기에 두 주를 쓰면 정작 학식 평점 기능을 만들 시간이 없습니다.

코드를 옮기는 방법

배포 — 한 번 만들어두면 계속 씁니다

배포는 내 컴퓨터의 코드를 사용자가 쓰는 곳으로 옮기는 일입니다. 요즘은 대부분 자동입니다.

  • 코드를 GitHub에 올리면 → 알아서 빌드하고 → 알아서 올라갑니다
  • 사람이 하는 일은 “이 코드를 올리겠다”고 결정하는 것뿐입니다
  • 그래서 발표 전날 새벽에도 똑같은 순서로 배포됩니다
  • 자동화의 진짜 이득은 “편하다”가 아니라 “매번 똑같다”입니다
배포는 프로젝트 마지막에 하지 마세요. 초반에 “아무것도 없는 빈 화면”을 먼저 배포해두고 시작하는 팀이 훨씬 안전합니다. 마지막 주에 처음 배포하다가 발표를 못 하는 팀이 매년 나옵니다.
실제로 Vercel · Supabase · Render에 올리는 과정은 이어지는 인프라 장들에서 화면과 함께 따라갑니다.

계층 (Tier)역할 및 책임주요 처리 작업

프론트엔드

현재 화면에서 눈에 보이는 모든 시각적 요소와 사용자의 조작을 담당합니다.

역할:

  • 백엔드에서 받아온 데이터(제목, 영상 링크, 추천 목록 등)를 브라우저에 보기 좋게 배치합니다.
  • 사용자가 '좋아요' 버튼을 누르거나 검색창에 글자를 입력하는 이벤트를 감지하여 백엔드로 전달합니다.

백엔드

실제 로직을 판단하고 처리하는 엔진입니다.

처리 로직 예시:

  • 페이지 로딩 시: 현재 로그인한 유저의 시청 기록과 취향을 분석하여 우측 상단에 띄울 '추천 동영상 목록'을 계산하고 결정합니다.
  • 좋아요 클릭 시: 로그인된 유저인지 검증하고, 이미 좋아요를 누른 영상인지 확인한 뒤 DB에 좋아요 수를 1 증가시키도록 요청합니다.
  • 댓글 작성 시 : 로그인된 유저인지 검증하고, DB에 사용자가 작성한 댓글 내용을 추가하도록 요청합니다.

데이터베이스

유튜브 서비스 운영에 필요한 모든 원본 정보가 영구적으로 저장되는 곳입니다.

저장되는 데이터:

  • 영상 정보 테이블: 영상 파일 경로, 제목, 업로드 날짜, 카테고리
  • 통계 데이터: 조회수(102만회), 좋아요 수(1.5만), 댓글 내용 및 등록 시간
  • 계정/채널 정보: 채널명(빵송국, 피식대학), 구독자 목록, 회원 로그인 정보

API는 클라이언트와 서버, 혹은 서로 다른 시스템 간에 정의된 규격에 따라 데이터를 주고받기 위한 인터페이스 명세입니다.

간단하게 표현하자면, 프론트엔드 ↔ 백엔드끼리 데이터를 주고 받기 위한 연결다리, 매개체 정도로 생각하면 됩니다.

1) HTTP 요청 (Request) 명세

  • Endpoint (URL): 요청을 전달할 서버의 네트워크 주소 및 자원 경로
    예: https://api.example.com/v1/posts
  • HTTP Method: 자원에 대해 수행할 작업의 종류
    • GET: 자원 조회
    • POST: 새로운 자원 생성
    • PUT / PATCH: 자원 전체 수정 / 일부 수정
    • DELETE: 자원 삭제
  • Headers: 메타데이터 및 인증 정보 (Content-Type, Authorization Bearer 토큰 등)
  • Body: 서버로 전송할 데이터 페이로드 (주로 POST, PATCH 시 사용)

2) HTTP 응답 (Response) 명세

  • Status Code: 요청 처리 결과를 나타내는 3자리 숫자 규격
    • 200 OK: 요청 성공
    • 201 Created: 자원 생성 성공
    • 401 Unauthorized: 인증 자격 증명 미비
    • 403 Forbidden: 해당 자원에 대한 접근 권한 없음
    • 404 Not Found: 요청한 엔드포인트 또는 자원이 존재하지 않음
    • 500 Internal Server Error: 서버 내부 런타임 에러 발생
  • Body (JSON): 경량화된 텍스트 기반 데이터 교환 포맷 (Key-Value 구조)

Vercel - 프론트엔드 배포

GitHub 저장소와 Vercel 계정을 연동해 두면, Vercel이 코드 변경 사항을 실시간 감지합니다.

코드를 수정하고 레포에 push하면 Vercel이 자동으로 소스코드를 불러와서 배포를 자동으로 진행합니다.

Vercel - Github 연동법

  1. 프론트엔드 배포용 레포 생성

  2. Vercel → Vercel 홈페이지 이동

  3. 로그인 진행 → Github로 로그인

  4. 접속 후 우측 상단에 있는 Add New > Project 클릭

  5. Import Git Repository 하단 박스 > Add GitHub Scope 선택

  6. 뜨는 창에서, 프론트엔드 배포용 레포가 존재하는 organization이나, account선택

  7. 선택 후, 접속된 페이지에서 스크롤을 조금 내려 Repository access 박스로 이동.
    Only select repositories > Select repositories에서 프론트 배포용 레포 선택

  8. 선택 후 Save > 레포 - vercel 연동 완료

  9. 다시 Import Git Repository > 추가된 레포 확인 및 import 버튼 클릭

  10. 환경 변수 및 기타 설정 후 Deploy 버튼을 누르면 배포 완료

  11. 배포된 서비스는 git push시마다 자동으로 업데이트 반영되어 재배포됨.

기능 하나를 끝까지

왜 하필 로그인인가

기능 하나를 골라 끝까지 파보려는 겁니다. 로그인을 고른 이유가 있습니다.

  • 거의 모든 서비스에 있습니다. 여러분 팀도 십중팔구 만들게 됩니다.
  • 이미 매일 쓰고 있습니다. 설명하기도, 이해하기도 좋습니다.
  • 인프라 파트에서 본 “직접 만들까 빌릴까”가 가장 잘 드러납니다. 두 달짜리 팀에게는 이 판단이 곧 일정입니다.
  • 잘못 만들면 사고가 납니다. 남의 계정이 털리는 건 버그 이상의 문제입니다.

먼저 두 단어를 구분합시다

인증과 인가는 다른 일입니다

한국어로도 영어로도 비슷하게 생겨서 헷갈립니다. 그런데 완전히 다른 질문입니다.

인증 — AUTHENTICATION
  • “너 누구야?”
  • 신분증을 확인하는 일
  • 건물 입구에서 사원증을 찍는 것
  • 실패하면 401 Unauthorized
인가 — AUTHORIZATION
  • “너 이거 해도 돼?”
  • 권한을 확인하는 일
  • 사원증으로 서버실 문이 열리는지
  • 실패하면 403 Forbidden
순서가 있습니다. 누구인지 모르면 자격도 따질 수 없습니다. 그래서 인증이 항상 먼저입니다.

문제의 출발점

서버는 여러분을 기억하지 못합니다

웹의 기본 구조상, 서버는 요청 하나하나를 처음 보는 사람처럼 대합니다. 방금 로그인한 사람이라는 걸 모릅니다.

  • 요청 1: “로그인할게요” → 서버: “확인했습니다”
  • 요청 2: “내가 쓴 리뷰 보여주세요” → 서버: “누구세요?”
  • 매번 아이디·비밀번호를 보내면? 보낼 때마다 새어나갈 위험이 생깁니다.
그래서 한 번만 확인하고, 대신 출입증을 줍니다. 이후로는 출입증만 보여주면 됩니다. 이 출입증을 토큰(token)이라고 부릅니다.

전체 흐름

로그인하고 나서 벌어지는 일

설계 판단의 예

출입증을 두 장 주는 이유

많은 서비스가 토큰을 두 종류 발급합니다. 왜 굳이 그럴까요 — 여기에 트레이드오프가 있습니다.

  • 짧게 만들면 훔쳐가도 금방 못 쓰게 됩니다. 대신 자주 만료돼서 사용자가 불편합니다.
  • 길게 만들면 편한데, 새어나갔을 때 오래 악용됩니다.
  • 그래서 짧은 것(액세스)을 요청마다 쓰고, 긴 것(리프레시)으로 조용히 갱신합니다.
이게 “로그인이 유지되는데도 안전한” 이유입니다. 편의와 안전이 충돌할 때 둘을 쪼개서 둘 다 가져간 것 — 설계란 이런 판단의 연속입니다.

지켜야 할 원칙

비밀번호는 저장하지 않습니다

데이터베이스에 비밀번호를 그대로 넣으면 안 됩니다. 되돌릴 수 없게 변환해서 저장합니다.

# 사용자가 입력한 것
inha1234

# 실제로 DB에 저장되는 것 (되돌릴 수 없음)
$2a$10$N9qo8uLOickgx2ZMRZoMye...

# 로그인할 때는 이렇게 확인합니다
입력값을 같은 방식으로 변환 → 저장된 값과 비교
→ 원문을 알 필요가 없습니다
그래서 “비밀번호 찾기”가 아니라 “비밀번호 재설정”인 겁니다. 어떤 서비스가 여러분의 비밀번호를 원문 그대로 알려준다면 그건 심각한 문제입니다. 여러분 서비스도 마찬가지입니다.

가장 실전적인 판단

로그인을 직접 만들 것인가

원리를 알았으니 이제 정해야 합니다. “만들 수 있다”와 “만들어야 한다”는 다릅니다.

직접 만들면 — 필요한 것 전부
  • 회원가입 폼과 입력 검증
  • 비밀번호 암호화 저장
  • 로그인 · 로그아웃 · 토큰 갱신
  • 비밀번호 재설정 (메일 발송까지)
  • 이메일 · 휴대폰 인증
  • 중복 가입 차단, 무차별 시도 방어
→ 팀 하나가 몇 주를 씁니다
빌리면
  • 구글 · 카카오 등 소셜 로그인 붙이기
  • 또는 인증 서비스 이용
    (Firebase Auth, Supabase Auth 등)
  • 비밀번호 관리·재설정·보안을 그쪽이 책임
→ 하루 이틀이면 붙습니다
두 달짜리 프로젝트에서 로그인에 몇 주를 쓰면, 정작 만들려던 것을 못 만듭니다. 로그인은 어느 서비스에나 있습니다 — 여러분 서비스만의 것이 아닙니다. 직접 만드는 시간은 그쪽에 쓰세요.

신분 확인이 끝난 뒤 VIP석인지 일반석인지 자리를 안내받는 것 — "이 사람이 무엇을 할 수 있는가"를 결정하는 단계.

02

인증은 어떻게 이루어질까

서비스마다 신분을 확인하는 방식이 다릅니다. 자주 만나게 될 네 가지만 짚어볼게요.

Session

세션 기반 로그인

로그인하면 서버가 세션을 만들고, 브라우저는 그 세션 ID를 쿠키로 들고 다녀요. 전통적인 웹사이트에서 가장 흔한 방식입니다.

Token

토큰 기반 (JWT)

서버가 상태를 저장하지 않고, 사용자 정보가 담긴 토큰을 발급해요. 앱과 API 서버가 분리된 서비스에서 많이 씁니다.

Delegated

소셜 로그인 (OAuth)

"Google로 로그인"처럼 다른 서비스에 신분 확인을 맡기는 방식. 이번 자료의 실습 파트에서 직접 다룹니다.

MFA

2단계 인증

비밀번호 하나로는 부족하니, 문자·앱 알림·지문 등 두 번째 확인 수단을 추가로 요구하는 방식이에요.

03

인가는 어떻게 이루어질까

인증만큼 자주 등장하진 않지만, 실무에서는 이 세 가지 이름을 알아두면 대화가 훨씬 편해져요.

RBAC

역할 기반 접근 제어

"관리자", "일반 회원"처럼 역할에 권한을 묶어두는 방식. 사람이 아니라 역할에 권한을 주기 때문에 관리가 쉬워요.

ACL

접근 제어 목록

파일이나 리소스마다 "누가 읽을 수 있는지·쓸 수 있는지" 목록을 직접 붙이는 방식. 구글 드라이브 공유 설정이 대표적이에요.

Scope

범위(Scope) 기반

"이 앱은 이메일 주소만 읽을 수 있음"처럼 권한의 범위를 좁게 쪼개는 방식. OAuth에서 핵심적으로 쓰이는 개념입니다.

05

실습: 구글 클라우드 콘솔에서 직접 발급받기

이제 개념은 충분해요. Google Cloud Console에서 새 프로젝트를 만들고, API 키와 OAuth 클라이언트 ID를 실제로 발급받는 과정을 화면과 함께 따라가 봅니다.

🎯 실습 목표

  1. Google Cloud 프로젝트 새로 만들기
  2. API 키 발급받기 (간단한 접근용 키)
  3. OAuth 동의 화면 구성하기 (로그인 동의창의 정체)
  4. OAuth 클라이언트 ID 발급받기 (Client ID / Secret)
주의 — API 키와 클라이언트 보안 비밀번호(Secret)는 비밀번호와 같아요. 화면 캡처, 깃허브 공개 저장소, 슬랙 메시지 어디에도 원본 값을 그대로 남기면 안 됩니다. 아래 화면들의 키·비밀번호 값은 실습을 마친 뒤 모두 삭제하고 가려서 실었습니다.
A

프로젝트 만들기

1

console.cloud.google.com에 접속해 상단 프로젝트 선택기에서 새 프로젝트를 누르고, 프로젝트 이름을 입력합니다. 이름은 나중에 URL의 일부(프로젝트 ID)가 되니 영문·하이픈으로 적어주세요.

프로젝트 이름을 입력하면 아래에 프로젝트 ID가 자동으로 표시돼요. 만들기를 누르면 몇 초 뒤 프로젝트가 생성됩니다.

B

API 키 발급받기

2

왼쪽 메뉴에서 API 및 서비스 → 사용자 인증 정보로 들어가면, 아직 아무것도 없는 빈 화면이 보여요. 이 프로젝트에서 처음 만드는 인증 정보를 여기서 관리하게 됩니다.

노란 경고는 "OAuth를 쓰려면 동의 화면부터 구성하라"는 안내예요. API 키만 만들 땐 무시해도 됩니다.

3

상단의 + 사용자 인증 정보 만들기를 누르면 세 가지 선택지가 나와요. 이 중 API 키와 OAuth 클라이언트 ID가 오늘의 주인공입니다.

API 키는 "간단한 접근 확인용", OAuth 클라이언트 ID는 "사용자 동의가 필요한 로그인용"이라고 구분하면 쉬워요.

4

API 키를 선택하면 이 키로 어떤 API에 접근할지 고르는 패널이 열립니다. 실무에서는 반드시 필요한 API로 제한해서 만들어야 해요.

만들기를 누르면 실제 키 문자열이 발급됩니다.

5

발급이 끝나면 이런 화면이 떠요. 이 값이 바로 ?key=API_KEY 형태로 요청에 붙이는 API 키예요.

※ 실제 키 값은 강의자료 공개를 위해 가렸습니다. 이 창을 닫으면 콘솔에서도 전체 값은 다시 보기 어려워요 — 바로 복사해두는 습관을 들이세요.

C

OAuth 동의 화면 구성하기

"Google로 로그인" 버튼을 눌렀을 때 뜨는 동의창, 그 내용을 정하는 단계예요. OAuth 클라이언트 ID를 만들기 전에 반드시 먼저 거쳐야 합니다.

6

credentials 화면의 동의 화면 구성 버튼을 누르면 "Google 인증 플랫폼"으로 이동해요. 아직 아무것도 설정되지 않은 상태입니다.

7

앱 이름과 사용자 지원 이메일을 입력합니다. 앱 이름은 사용자가 동의 화면에서 보게 될 이름이에요.

※ 지원 이메일 칸은 개인정보 보호를 위해 가렸습니다.

8

대상 단계에서는 내부(조직 내부 사용자만)와 외부(구글 계정이 있는 누구나, 테스트 모드로 시작) 중 고릅니다. 개인 실습이라면 대부분 외부를 선택해요.

9

연락처 이메일까지 입력하면 마지막으로 Google API 서비스 데이터 정책 동의 체크박스가 남아요. 네 단계 모두 초록 체크가 되면 만들기를 누릅니다.

D

OAuth 클라이언트 ID 발급받기

10

동의 화면 구성이 끝났다면 다시 사용자 인증 정보로 돌아와 OAuth 클라이언트 ID를 선택합니다. 먼저 애플리케이션 유형을 고르는데, 웹사이트라면 웹 애플리케이션을 선택해요.

11

가장 중요한 입력값은 승인된 리디렉션 URI예요. 사용자가 로그인을 마치고 돌아올 주소를 미리 등록해두는 칸으로, 여기 등록 안 된 주소로는 절대 돌아갈 수 없습니다.

예: https://내앱주소.com/callback — 로컬 개발 중이라면 http://localhost:3000/callback처럼 등록해두면 됩니다.

12

만들기를 누르면 클라이언트 ID와 클라이언트 보안 비밀번호(Secret)가 한 번에 발급됩니다. 이 창을 닫으면 Secret은 다시 볼 수 없으니 바로 안전한 곳(예: .env 파일)에 복사해두세요.

※ 클라이언트 ID·Secret 값은 강의자료 공개를 위해 가렸습니다. 실습이 끝난 뒤에는 이 자료를 만들며 사용한 데모 프로젝트와 키를 곧바로 삭제했습니다.

실습 후 정리 — 테스트로 만든 프로젝트·API 키·OAuth 클라이언트는 실습이 끝나면 IAM 및 관리자 → 리소스 관리에서 프로젝트째로 삭제하거나, 사용자 인증 정보 목록에서 각 항목을 개별 삭제하세요. 쓰지 않는 키를 남겨두는 것 자체가 보안 위험입니다.

정리하며

  • 인증은 "누구인지" 확인하는 것, 인가는 "무엇을 할 수 있는지" 정하는 것 — 인증이 먼저입니다.
  • 인증에는 세션, 토큰(JWT), OAuth, 2단계 인증 등 다양한 방식이 있습니다.
  • OAuth는 비밀번호를 넘기지 않고 필요한 권한만 위임하는 구조이며, 리소스 소유자·클라이언트·인가 서버·리소스 서버 네 주체로 이루어집니다.
  • Google Cloud Console에서는 사용자 인증 정보 메뉴에서 API 키와 OAuth 클라이언트 ID를 발급하며, OAuth는 반드시 동의 화면 구성이 먼저입니다.
  • API 키와 클라이언트 Secret은 비밀번호와 동급으로 다루고, 다 쓴 실습용 키는 바로 삭제하세요.

코드를 쓰는 곳 — 에디터(IDE)

코드를 쓰고, 파일을 보고, 터미널을 여는 일을 한 화면에서 하는 프로그램입니다. 설치는 “설치할 것 네 가지”에서 끝냈습니다 — 여기서는 열어서 무엇이 어디 있는지만 봅니다.

  • Antigravity를 기본으로 씁니다. 무료이고, AI 에이전트가 이미 들어 있어서 따로 결제하거나 설정할 것이 없습니다.
  • VS Code를 이미 쓰고 있다면 그대로 쓰셔도 됩니다. Antigravity가 VS Code를 바탕으로 만든 에디터라서 화면 구성과 단축키가 거의 같습니다 — 왼쪽 탐색기, 가운데 편집기, 아래 터미널. 이 장의 설명은 양쪽에 그대로 적용됩니다.
  • VS Code에서 에이전트를 쓰려면 GitHub Copilot 같은 확장을 따로 붙여야 합니다. 그게 번거로우면 Antigravity가 편합니다.
결제는 나중에 생각해도 됩니다. 팀 프로젝트는 무료 도구만으로 끝까지 만들 수 있습니다. 더 깊게 쓰고 싶어진 사람만 유료 구독을 고민하세요.

터미널에서 AI 에이전트 부르기

에이전트는 터미널에 이름을 치면 실행됩니다. 에이전트는 지금 터미널이 있는 폴더 — 즉 열어 둔 프로젝트 — 를 읽고 작업합니다.

1

프로젝트 폴더의 터미널에서 설치한 에이전트 이름을 입력합니다. 화면은 Claude Code(claude)이고, 다른 도구도 똑같이 이름만 치면 됩니다 — gemini, codex, copilot.

claude

처음 실행하면 “이 폴더를 믿느냐”고 묻습니다. 내 프로젝트가 맞으면 허용합니다.

2

입력창에 할 일을 한국어로 씁니다. 처음에는 읽기만 시키는 부탁으로 감을 잡아 보세요. 아래는 “README.md를 읽고 이 레포가 어떤 레포인지 두 줄로 설명해 줘. 파일은 수정하지 마.”라고 시킨 결과입니다.

화면에서 볼 것: “Read 1 file” — 에이전트가 실제로 파일을 열어 읽었다는 기록입니다. 에이전트는 무엇을 읽고, 고치고, 실행했는지 이렇게 남깁니다. 결과만 보지 말고 이 기록을 같이 보는 습관을 들이세요.
끝낼 때는 /exit 또는 Ctrl + C 두 번. 에이전트가 파일을 고쳤다면 커밋하기 전에 바뀐 내용을 꼭 직접 확인하세요 — 이유는 “사고 없이 쓰기” 장에 있습니다.
Antigravity에는 오른쪽에 Agent 패널이 따로 있고, VS Code에도 Copilot 채팅 패널이 있습니다. 터미널 방식과 하는 일은 같습니다. 이 핸드북은 어떤 에디터에서든 똑같이 쓸 수 있는 터미널 방식을 기준으로 합니다.

한 걸음 더

GitHub CLI — 터미널에서 깃허브까지

에이전트는 터미널에서 할 수 있는 일을 대신 해 줍니다. 그래서 GitHub CLI(gh)를 깔아 두면, 브랜치 만들기부터 커밋·push·PR 올리기까지 말로 시킬 수 있습니다.

1

설치 — cli.github.com에서 받거나, 터미널에서 한 줄로 설치합니다.

# Windows
winget install --id GitHub.cli

# macOS
brew install gh
2

로그인 — 한 번만 하면 됩니다. 브라우저가 열리고 코드를 입력하면 끝입니다. 이후로는 git push할 때 비밀번호를 묻지 않습니다.

gh auth login
3

자주 쓰는 명령 — 앞의 깃허브 파트에서 웹 화면으로 했던 일과 똑같습니다.

gh repo clone Mybread2/github-practice   레포 받기
gh pr create                             PR 올리기 (제목·설명을 물어봄)
gh pr view --web                         내 PR을 브라우저로 열기
gh pr status                             내 PR들이 어떤 상태인지
여기서부터가 재미있는 부분입니다. gh가 깔려 있으면 에이전트에게 이렇게 시킬 수 있습니다 — “지금 바꾼 것들 커밋하고, feature/review-write 브랜치로 push한 다음 PR 올려 줘. 설명에는 무엇을 바꿨는지 적어 줘.” 에이전트가 터미널에서 git과 gh를 차례로 실행합니다.
대신 여기서부터는 되돌리기가 어려워집니다. 커밋은 되돌릴 수 있지만, 올라간 PR은 팀원들이 이미 봅니다. 그래서 두 가지만 지키세요.
  • 무엇을 커밋할지 먼저 확인하기 — git status로 바뀐 파일을 보고 나서 시키세요. .env 같은 파일이 딸려 올라가면 큰일입니다.
  • main에는 직접 시키지 않기 — 항상 내 브랜치에서. 사람이 하든 에이전트가 하든 규칙은 같습니다.
PR을 웹에서 만드는 방법은 “Pull Request 올리기”에 화면과 함께 있습니다. 둘 중 편한 쪽을 쓰면 됩니다 — 결과는 똑같은 PR입니다.

기본 세 가지

일단 이것만 지키세요

  1. 맥락을 줍니다. “로그인 고쳐줘”가 아니라 “이 파일에서, 이런 증상이 나는데, 이렇게 동작해야 합니다”. 앞에서 본 “잘 물어보는 법”과 똑같습니다.
  2. 작게 시킵니다. 한 번에 하나. 열 개를 한꺼번에 시키면 어디서 틀렸는지 못 찾습니다.
  3. 결과를 반드시 확인합니다. 실행해보고, 읽어보고, 이해가 안 되면 물어봅니다. 이해 못 한 코드는 팀 코드에 넣지 않습니다.
눈치채셨겠지만 협업하는 법에서 본 원칙과 거의 같습니다. 에이전트를 잘 쓰는 건 결국 일을 잘 설명하고 결과를 확인하는 능력입니다 — 사람에게든 도구에게든.

조심할 것

그럴듯하게 틀립니다

이게 가장 위험한 특성입니다. 틀릴 때도 자신 있는 말투입니다.

  • 없는 함수를 만들어냅니다. 이름이 그럴듯해서 있는 줄 압니다.
  • 오래된 방식을 알려줍니다. 라이브러리가 바뀌었는데 예전 사용법을 씁니다.
  • 여러분 팀의 약속을 모릅니다. 팀이 정한 구조를 무시한 코드를 줄 수 있습니다.
  • 비밀정보를 붙여넣지 마세요. 비밀번호, API 키, 설정 파일 내용은 안 됩니다.
판단 기준 하나만 기억하세요. “이걸 왜 이렇게 했는지 내가 팀원에게 설명할 수 있나?” 설명 못 하면 아직 내 코드가 아닙니다. PR에 올리면 안 됩니다.

처음 세 문장

세 문장으로 남기면

  1. 개발자는 주어진 시간과 예산 안에서 문제를 소프트웨어로 해결하는 사람입니다. 그래서 “제일 좋은 기술”이 아니라 “이 제약에 맞는 선택”을 합니다.
  2. 개발자는 언어를 아는 사람이 아니라 시스템을 설계할 수 있는 사람입니다. 무엇을 만들고 무엇을 안 만들지 정하는 일이 설계입니다.
  3. 서비스는 화면 · 판단 · 기억으로 나뉘고, 그 사이를 API라는 약속이 잇습니다. 그 덕에 팀이 나눠 일할 수 있습니다.
팀에 배정되면 첫 주에 코딩부터 시작하지 마세요. 이 순서대로 — 문제를 정하고, 안 만들 것을 정하고, 데이터를 그려보고, 그다음에 시작하세요.

로그인 정리

로그인, 세 문장으로

  1. 인증은 “누구냐”, 인가는 “해도 되냐”입니다. 순서가 있고, 실패했을 때 나오는 번호도 다릅니다(401 / 403).
  2. 원리는 알되, 직접 만들지는 마세요. 두 달짜리 팀에게 로그인은 빌려 쓰는 게 거의 항상 맞습니다.
  3. 화면에서 숨기는 것은 보안이 아닙니다. 막는 일은 언제나 서버에서 합니다.

마치며

도구는 바뀌어도 이건 안 바뀝니다

개발자는 주어진 시간과 예산 안에서 문제를 소프트웨어로 해결하는 사람이고,
언어를 아는 사람이 아니라 시스템을 설계할 수 있는 사람입니다.

  • 제약을 보는 눈 — 어떤 기술을 배우든, 판단의 기준은 항상 “이 상황에서 맞는가”입니다
  • 쪼갤 줄 아는 능력 — 문제를 만들 수 있는 조각으로 나누는 일은 언어가 바뀌어도 그대로입니다
  • 설명하고 읽는 능력 — 혼자 만드는 서비스는 없습니다
  • 확인하는 습관 — 도구가 성공이라고 말할 때, 그게 무엇의 성공인지 물어보는 사람이 사고를 막습니다

✓

이제 팀에서 만들 차례입니다

여기서 들은 건 전부 팀 프로젝트에서 실제로 쓰게 될 것들입니다. 막히면 멘토에게 — 여기서 배운 방식으로 — 물어보세요. 자료는 링크로 남으니 언제든 다시 보시고요.
